# Ant2 v2.4.4 — WAF Port 80 Bypass Fix

Working session diagnosing and fixing a silent WAF bypass on all hosts with `force_https=true` across all production servers.

## Abstract

southex-th.com on server 172.20.20.181 proxied requests correctly but [[ModSecurity]] was inactive when Cloudflare connected directly on port 80. Root cause: `generateNginxConf()` in `nginxConfig.js` had three server block branches — the `force_https=true` port 80 branch was missing `${wafBlock}`. The Cloudflare-safe proxy path (skip redirect when `X-Forwarded-Proto: https`, proxy directly) was added to this block without carrying over the WAF directives. Fixed in [[Ant2-Proxy-Security-Manager]] v2.4.4 by adding all security blocks to the force_https port 80 template. Server 181 host_5 was live-patched; servers 180 and 238 require a full rebuild.

## Key Takeaways

- **Silent WAF bypass on port 80 CF-safe block** — `force_https=true` hosts had `modsecurity on` missing from the port 80 server block. CF connects to origin on port 80 with `X-Forwarded-Proto: https` → `proxy_pass` fires → WAF never ran. The GUI showed "Block mode" but attacks via CF on port 80 were not inspected.
- **Blast radius is all servers, all force_https hosts** — The default production configuration. Port 443 blocks were unaffected; only CF-proxied port 80 traffic was unprotected. Servers 180 and 238 need a full rebuild to apply the code fix.
- **WAF follows `proxy_pass`, not just SSL** — Any NGINX server block containing `proxy_pass` must have `modsecurity on`. The bug happened because the CF-safe proxy path was added to the port 80 block after the original design (port 80 = redirect only), without carrying over WAF directives. See [[waf-proxy-pass-scope]].
- **Two-layer fix required** — Code fix in `nginxConfig.js` prevents future configs from having the bug. Existing deployed configs (container volumes) are NOT updated until `docker compose up --build` per server.
- **Detection gap in UI** — WAF mode showed "Block mode" and port 443 attacks were blocked, creating false confidence. No indicator that port 80 traffic was uninspected.

## Notable Details

### Bug Location

`api/src/services/nginxConfig.js` — `generateNginxConf()` function:

| Branch | Port 80 WAF | Port 443 WAF |
|--------|-------------|--------------|
| `force_https=false` | ✓ included | ✓ included |
| `force_https=true` (CF-safe) | ✗ **missing** | ✓ included |
| No SSL | ✓ included | n/a |

### Fix Applied

Added `${exploitBlock}`, `${accessListBlock}`, `${wafIpBlock}`, `${ipBlockBlock}`, `${countryBlock.serverBlock}`, `${rateLimitBlock}`, `${wafBlock}`, `${countryBlockedPage}`, `${ipBlockedPage}`, `${wafBlockedPage}` to the `force_https=true` port 80 template before the `location /` block.

### Live Server Patch (181 host_5.conf)

Injected into port 80 server block:
```nginx
modsecurity on;
modsecurity_rules_file /etc/modsecurity.d/custom/host_5.conf;
error_page 403 /waf-blocked.html;
location = /waf-blocked.html { ... }
```
`nginx -t` → OK. `nginx -s reload` → RELOADED OK.

## Gaps / Unanswered Questions

- Servers 172.20.20.180 and 192.168.0.238: all `force_https=true` hosts remain affected until full rebuild.
- No audit performed to count how many hosts across all servers have `force_https=true`.
- The UI has no indicator distinguishing "WAF active on both ports" vs "WAF active on port 443 only".
