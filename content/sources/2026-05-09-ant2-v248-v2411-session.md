# Ant2 v2.4.8–v2.4.11 Session: Jail/Block Pipeline Fixes

Source file: `raw/ant2-v248-v2411-session.md`

## Abstract

Four-version release cycle (v2.4.8 → v2.4.11) focused entirely on correctness of the IP jail and block pipeline. Six bugs fixed: default server blocking gap, asymmetric release coupling, missing `row2host()` wrapper, inotify reload latency, missing domain visibility in the jail UI, and a critical lazy-ingestion bug that caused zero auto-jails despite real WAF blocks.

## Key Takeaways

- **Default server was unprotected.** `_default_site.conf` had no geo block. Any attacker omitting the `Host:` header bypassed all jail and IP block rules. Fix: `writeDefaultSiteConfig()` now injects a combined `geo $remote_addr $ip_blocked_default` block, returning 423 on match. Each include file uses a unique variable name to avoid http-context naming conflicts.

- **Block deletion didn't fully release.** `DELETE /api/ipblock/global/:id` deleted from `ip_block_rules` but left the matching row in `ip_jail`. Fix: both DELETE handlers extract the bare IP via `rule.ip_prefix.split('/')[0]`, then delete from `ip_jail` and clear the Redis counter key `jail:cnt:<ip>`.

- **`row2host()` was missing from ipblock.js.** `writeHostConfig()` expects a parsed host object (with `paths` as array); `ipblock.js` was passing raw SQLite rows. Silent misconfiguration. Fix: added `row2host` to the import from `nginxConfig.js`.

- **inotify reload latency caused 423 to persist after release.** `writeAllHostConfigs()` writes N+1 files; the WAF container's inotify debounce loop resets on each file event, accumulating multi-second delay. Fix: `reloadNginxNow()` calls `docker exec ant2proxy-waf nginx -s reload` directly via `execSync`. The API container has the Docker socket mounted and `docker-cli` installed. Called at end of all config-write paths.

- **Jail UI had no domain context.** Added `domains[]` to `GET /api/jail` response (last 7 days of `waf_events` joined to `hosts`). `IpJail.jsx` now shows an expandable "Domains" column with Globe/ChevronDown toggle and domain chips.

- **Lazy WAF log ingestion silently broke auto-jail.** `ingestWafLogs()` in `logs.js` was only triggered from WAF log UI routes (`/waf/timeseries`, `/waf/top-ips`, etc.). `pollAttacks()` reads from `waf_events` SQLite — if the UI route was never hit, the table had no new rows, Redis counters were never incremented, and no IP was ever auto-jailed. Evidence: pentest fired 19 WAF 403s but zero IPs appeared in jail. Fix: `pollAttacks()` now calls `maybeIngestWafLogs()` at start of every 30s poll cycle. `maybeIngestWafLogs()` has its own 30s rate limiter so it's a no-op if called too often.

## Notable Quotes / Details

> "Pentest fired 27/27 attacks, 19 returned 403 from the WAF, but zero IPs appeared in Attack Counters or the Jail list."

This was the evidence that confirmed the lazy-ingestion bug. The WAF was working; the ingestion pipeline was not.

The WAF audit log pipeline in full:
```
ModSecurity audit logs → ingestWafLogs() → waf_events SQLite
  → pollAttacks() → Redis jail:cnt:* → ip_jail → writeAllHostConfigs()
  → nginx geo block → HTTP 423
```

`pollAttacks()` was the consumer of `waf_events` but never the producer; `ingestWafLogs()` was the producer but only called on-demand. The fix closes this gap by making `pollAttacks()` trigger ingestion itself.

## Gaps / Unanswered Questions

- Why do some ModSecurity blocks return `000` (connection reset) vs `403` in the pentest script? This may be WAF TCP-reset behavior for specific rule matches.
- The mixed 423/403/000 responses in the pentest (with baseline 423) suggest ModSecurity can fire before the nginx geo block in some cases — execution order not fully understood.
- `maybeIngestWafLogs()` rate-limiter uses a module-level variable; if the API process restarts, the rate limit resets immediately.
