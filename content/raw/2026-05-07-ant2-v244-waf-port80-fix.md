# Ant2 v2.4.4 — WAF Port 80 Bypass Fix Session Notes — 2026-05-07

## Context
Bug report: southex-th.com on server 172.20.20.181 — WAF blocked attacks when traffic came via CF → front NGINX NPM → WAF 181, but NOT when CF connected directly to WAF 181 (CF DNS only / direct proxy mode). Proxy was working; only ModSecurity was inactive.

---

## 1. Diagnosis

### Topology Comparison

| Path | WAF status |
|------|-----------|
| CF → front NPM → WAF 181 → web | WAF active (NPM connects to WAF on port 443 HTTPS block) |
| CF → WAF 181 → web | WAF inactive (CF connects on port 80 — missing modsecurity) |
| CF DNS only → WAF 181 → web | WAF inactive (direct HTTP on port 80 — same missing block) |

### Root Cause Found

`nginxConfig.js` `generateNginxConf()` function generates three distinct NGINX server blocks:

1. **`force_https=false` port 80 block** (lines 484–509) — includes `${wafBlock}` ✓
2. **`force_https=true` port 80 block** (lines 447–483) — **missing `${wafBlock}`** ✗
3. **Port 443 HTTPS block** (lines 511–546) — includes `${wafBlock}` ✓

The `force_https=true` port 80 block uses the "Cloudflare-safe" double-variable redirect pattern:
```nginx
set $https_redirect 1;
if ($http_x_forwarded_proto = "https") { set $https_redirect 0; }
if ($https_redirect = 1) { return 301 https://$host$request_uri; }
proxy_pass https://...;
```

When CF sends `X-Forwarded-Proto: https`, `$https_redirect=0` → redirect is skipped → request is proxied directly. But `modsecurity on` was not in this server block, so ModSecurity never ran.

### Blast Radius

**All hosts with `force_https=true` on all servers had WAF inactive for CF proxy traffic on port 80.** This is the most common production configuration. The WAF appeared to work because:
- CF proxy users saw the GUI as "Block mode" (setting was correct)
- Attacks arriving via HTTPS (port 443) were blocked normally
- Only attacks arriving via CF on port 80 (the actual CF→origin connection) bypassed WAF

---

## 2. Code Fix — nginxConfig.js

**File**: `api/src/services/nginxConfig.js`

Added all security blocks to the `force_https=true` port 80 server block:

```javascript
// Before fix — force_https=true port 80 block had only:
${acmeBlock}

location / {
    // CF-safe proxy...
}

// After fix — added full security context before location /:
${acmeBlock}
${exploitBlock}
${accessListBlock}
${wafIpBlock}
${ipBlockBlock}
${countryBlock.serverBlock}
${rateLimitBlock}
${wafBlock}           // ← modsecurity on + modsecurity_rules_file
${countryBlockedPage}
${ipBlockedPage}
${wafBlockedPage}     // ← error_page 403 + location = /waf-blocked.html

location / {
    // CF-safe proxy...
}
```

1. `docker cp ant2proxy-waf:/etc/nginx/conf.d/host_5.conf /tmp/host_5.conf`

## 6. Key Architectural Finding

The bug existed because the "Cloudflare-safe" redirect logic creates a third traffic path (CF on port 80, proxied not redirected) that was not present in the original port 80 design (port 80 = redirect only). When the CF-safe proxy path was added to the force_https block, the WAF directives that belonged in every proxy path were not carried over.

**Rule going forward**: Any NGINX server block that contains a `proxy_pass` directive must also have `modsecurity on` and `modsecurity_rules_file` if WAF is enabled for that host. The WAF context follows `proxy_pass`, not just SSL.
